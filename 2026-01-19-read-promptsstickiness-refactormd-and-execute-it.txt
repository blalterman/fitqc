  Phase 2: Design with Propositions

  2.1 Core Function Signature

  Question: Should we create a unified detect_stickiness() function?

  Proposed Unified API

  def detect_stickiness(
      x: NDArray,
      ref: float,        # Reference point (x0, L, or U)
      L: float,          # Lower bound
      U: float,          # Upper bound
      mode: Literal["interior", "lower", "upper"],
      config: StickinessConfig,
  ) -> StickinessResult

  Proposition

  For:
  - Reduces code duplication (shared mass curve computation, elbow detection)
  - Single mental model for users ("detect stickiness at a reference point")
  - Easier to maintain and test one function
  - Interior and boundary are mathematically identical: measure distance from reference, detect spike at 0

  Against:
  - Interior uses histogram-based spike detection with find_peaks; boundary uses excess-mass-ratio
  - Interior uses log-spaced grid; boundary uses linear-spaced grid
  - Different config parameters mean the "unified" function still needs mode-specific logic
  - Forces one config type to handle both cases (or we need mode-specific configs anyway)
  - The two detection algorithms are conceptually different despite similar structure

  Decision: DO NOT unify into single function. The detection algorithms differ too much (histogram spike vs excess ratio). Instead, extract shared utilities (mass curve computation) while keeping run_interior_qc and run_boundary_qc as separate top-level APIs. Move both into stickiness.py as a consolidation, not a true merge.

  ---
  2.2 Backward Compatibility

  Options:
  - A) Delete interior.py/boundary.py entirely, update all imports
  - B) Keep interior.py/boundary.py as thin wrappers that call stickiness.py
  - C) Keep old function names as aliases in stickiness.py

  Option A: Delete old modules, update imports

  For:
  - Cleanest solution - no legacy code to maintain
  - Clear migration path for users
  - Forces codebase to use new canonical locations

  Against:
  - Breaking change for any external users importing from fitqc.interior import ...
  - Requires updating all internal imports (8 files)
  - No deprecation period

  Option B: Keep as thin wrappers

  For:
  - Full backward compatibility - existing code keeps working
  - Gradual deprecation possible (add warnings)
  - Low risk - can test new code while old paths still work

  Against:
  - Two code paths to maintain
  - Users might not discover the new consolidated module
  - Indirection adds complexity

  Option C: Aliases in stickiness.py, delete old modules

  For:
  - Single source of truth in stickiness.py
  - Can provide both old names (e.g., run_interior_qc) and new names
  - Clean module structure

  Against:
  - Import path changes (from fitqc.stickiness vs from fitqc.interior)
  - Aliases might be confusing (two names for same function)

  Decision: Option A - Delete old modules, update all imports.

  Rationale: This is an internal refactor of a v0.1.0 package without external users. The __init__.py already re-exports the public API, so users importing from fitqc directly (from fitqc import run_interior_qc) won't be affected. Only internal imports need updating.

  ---
  2.3 Test Strategy

  Options:
  - A) Merge test_interior.py + test_boundary.py → test_stickiness.py
  - B) Keep separate test files, update imports
  - C) Create new test_stickiness.py, keep old tests for regression

  Option A: Merge into test_stickiness.py

  For:
  - Mirrors the module consolidation (one module → one test file)
  - Easier to see all stickiness tests together
  - Can refactor shared test fixtures

  Against:
  - Large test file (~500 lines combined)
  - Loses logical grouping (interior tests vs boundary tests)
  - Git history becomes harder to trace

  Option B: Keep separate test files, update imports

  For:
  - Minimal changes to test structure
  - Clear separation of interior vs boundary test coverage
  - Easy to maintain and navigate

  Against:
  - Test files don't match module structure (test_interior.py tests stickiness.py)
  - Confusing naming

  Option C: Create new + keep old

  For:
  - Can add new unified tests while preserving existing coverage
  - Regression safety

  Against:
  - Duplicate test coverage
  - Maintenance burden

  Decision: Option B - Keep separate test files, update imports only.

  Rationale: The tests are well-organized by concept (interior vs boundary). Renaming to test_stickiness_interior.py and test_stickiness_boundary.py would be pedantic. Simply updating the import from from fitqc.interior import ... to from fitqc.stickiness import ... preserves all test coverage with minimal churn.

  ---
  2.4 Result Dataclass

  Question: Should InteriorResult and BoundaryResult merge into StickinessResult?

  Proposition

  For:
  - Single result type simplifies the API
  - Similar field structure (detected flag, threshold, curves)
  - Users don't need to learn two result types

  Against:
  - Field names differ semantically:
    - Interior: spike_detected, spike_z_loc, eps_star, hist_counts, hist_edges
    - Boundary: lower_pileup_detected, upper_pileup_detected, t_lo_star, t_hi_star
  - Merging would require:
    - Generic field names (loses domain meaning), OR
    - Optional fields everywhere (messy API), OR
    - Mode-specific subclasses (no real simplification)
  - Plot functions rely on specific field names
  - Report JSON schema would change

  Decision: Keep InteriorResult and BoundaryResult separate.

  Rationale: The result types encode domain-specific semantics (spike vs pileup, single vs dual reference). A unified type would either lose this meaning or become overly complex with optional fields. The current types are clear and self-documenting.

  Question 1: Unified StickinessResult

  Current Result Structures

  @dataclass
  class InteriorResult:
      spike_detected: bool
      spike_z_loc: float | None      # z-location of spike (unique to interior)
      eps_star: float | None         # threshold (analogous to t_lo_star/t_hi_star)
      eps_grid: NDArray              # search grid
      mass_curve: NDArray            # P(z < eps)
      hist_counts: NDArray           # histogram data (unique to interior)
      hist_edges: NDArray            # histogram edges (unique to interior)

  @dataclass  
  class BoundaryResult:
      lower_pileup_detected: bool    # two detection flags (vs one)
      upper_pileup_detected: bool
      t_lo_star: float | None        # lower threshold
      t_hi_star: float | None        # upper threshold
      tol_grid: NDArray              # search grid (analogous to eps_grid)
      lower_mass_curve: NDArray      # P(u < tol)
      upper_mass_curve: NDArray      # P(1-u < tol) - two curves (vs one)

  Proposed Unified Structure

  @dataclass
  class StickinessResult:
      """Result from any stickiness detection."""
      mode: Literal["interior", "lower", "upper"]
      detected: bool
      threshold: float | None        # eps_star, t_lo_star, or t_hi_star
      reference_point: float         # x0, L, or U
      grid: NDArray                  # eps_grid or tol_grid
      mass_curve: NDArray            # the relevant mass curve

      # Interior-specific (None for boundary)
      spike_z_loc: float | None = None
      hist_counts: NDArray | None = None
      hist_edges: NDArray | None = None

  FOR Unified StickinessResult

  F1. Uniform Iteration
  With unified results, users can process all stickiness checks uniformly:
  results = detect_stickiness(x, x0, L, U, mode="all")
  for result in results:
      if result.detected:
          print(f"{result.mode} stickiness at threshold {result.threshold}")
  Evidence: The run_qc() function in report.py:226-259 already iterates over parameters. A unified result type simplifies this pattern.

  F2. Simplified Mask Building
  Current _build_mask() in report.py:270-329 has three separate code blocks for interior/lower/upper. With unified results:
  for result in results:
      if result.detected and result.threshold is not None:
          stuck = compute_distance(x, result.reference_point, L, U) < result.threshold
          mask = mask & ~stuck

  F3. JSON Schema Consistency
  A single result schema is easier to document and validate than two different schemas.

  F4. Future Extensibility
  If we add new stickiness types (e.g., "midpoint stickiness"), they fit the same structure.

  AGAINST Unified StickinessResult

  A1. Loss of Type Safety
  With separate types, the type checker knows exactly what fields exist:
  def process_interior(r: InteriorResult) -> None:
      print(r.hist_counts)  # Type checker knows this exists

  def process_boundary(r: BoundaryResult) -> None:
      print(r.hist_counts)  # Type error! Field doesn't exist
  With unified type and optional fields, errors become runtime instead of compile-time.

  A2. Awkward Optional Fields
  hist_counts and hist_edges only make sense for interior. Making them Optional means:
  - Users must check if result.hist_counts is not None before use
  - IDE autocomplete shows fields that may not apply
  - Documentation must explain "only populated when mode='interior'"

  A3. Semantic Mismatch
  InteriorResult.spike_detected and BoundaryResult.lower_pileup_detected describe different phenomena:
  - Spike: a narrow histogram peak (detected via find_peaks)
  - Pileup: excess mass near boundary (detected via ratio check)

  Calling both detected: bool loses this semantic distinction.

  A4. Breaking Change
  Existing code using InteriorResult and BoundaryResult would need updates. The current types are part of the public API (exported in __init__.py).

  A5. Two Curves vs One
  BoundaryResult has lower_mass_curve AND upper_mass_curve. The unified type has one mass_curve. For boundary mode, which curve goes there? We'd need to either:
  - Split into two results (lower and upper separately) - changes semantics
  - Keep both curves - back to having boundary-specific fields

  DECISION NEEDED

  Option 1A: Unified StickinessResult with optional fields for mode-specific data

  Option 1B: Keep separate InteriorResult and BoundaryResult, wrapper returns union type InteriorResult | BoundaryResult

  Option 1C: Keep separate result types, but add a common StickinessResultProtocol they both implement for shared fields

  My lean: 1B (keep separate types, return union) because it preserves type safety and avoids breaking changes. The wrapper's return type would be:
  def detect_stickiness(..., mode: str) -> InteriorResult | BoundaryResult | list[InteriorResult | BoundaryResult]

  Question 4: Detect-All Mode

  Proposed API

  # Single mode
  result = detect_stickiness(x, x0, L, U, mode="interior")  # Returns InteriorResult

  # All modes
  results = detect_stickiness(x, x0, L, U, mode="all")  # Returns list of 3 results
  # results[0]: InteriorResult (x0 stickiness)
  # results[1]: BoundaryResult with lower info
  # results[2]: BoundaryResult with upper info
  # OR: Returns a combined object?

  FOR Detect-All Mode

  F1. Common Use Case
  Looking at report.py:226-248, the run_qc() function always runs BOTH interior and boundary QC for each parameter. A detect-all mode matches this common pattern.

  Evidence:
  # Current code in run_qc():
  interior_result = run_interior_qc(x=x, x0=x0, L=L, U=U, config=interior_config)
  boundary_result = run_boundary_qc(x=x, L=L, U=U, config=boundary_config)
  Users who want comprehensive QC currently make two calls. One call is simpler.

  F2. Atomic Operation
  All three checks share input data (x, L, U). Running them together ensures consistent analysis of the same dataset.

  F3. Performance Opportunity
  With all three in one call, we could potentially share computation:
  - Sort x once, reuse for all mass curves
  - Compute u = (x-L)/(U-L) once, use for both lower and upper

  (Current implementation doesn't share, but detect-all enables future optimization.)

  AGAINST Detect-All Mode

  A1. Return Type Complexity
  What does mode="all" return?

  Option A: list[InteriorResult | BoundaryResult] - loses structure
  Option B: tuple[InteriorResult, BoundaryResult] - clearer but BoundaryResult has both lower/upper
  Option C: AllStickinessResult dataclass - yet another type to maintain
  Option D: dict[str, InteriorResult | BoundaryResult] - stringly-typed

  None of these is clearly superior.

  A2. Config Complexity
  Interior and boundary use different configs:
  detect_stickiness(..., mode="all", config=???)
  Do we pass:
  - Two separate configs? interior_config=..., boundary_config=...
  - A combined config? More coupling
  - Use defaults only for all mode? Less flexible

  A3. Partial Failure Handling
  What if interior detection succeeds but boundary fails (or vice versa)? With separate calls, this is clear. With all mode, we need error handling strategy.

  A4. YAGNI (You Aren't Gonna Need It)
  Users who want all checks can call the wrapper three times:
  interior = detect_stickiness(x, x0, L, U, mode="interior")
  lower = detect_stickiness(x, L, L, U, mode="lower")
  upper = detect_stickiness(x, U, L, U, mode="upper")
  Three lines isn't burdensome. Adding all mode for marginal convenience adds API surface.

  Proposed Return Type for All Mode

  If we do implement all mode, I propose:

  @dataclass
  class AllStickinessResults:
      interior: InteriorResult
      lower: BoundaryResult  # Only lower_pileup_detected is meaningful
      upper: BoundaryResult  # Only upper_pileup_detected is meaningful

  Wait - this reveals a problem. BoundaryResult contains BOTH lower and upper detection. If we call run_boundary_qc(), we get both in one result. So "all mode" is really just:

  results = (run_interior_qc(...), run_boundary_qc(...))  # That's it

  The boundary result already has both boundaries. So all mode would return:
  tuple[InteriorResult, BoundaryResult]  # Interior + (Lower AND Upper)

  DECISION NEEDED

  Option 4A: Implement all mode, returns tuple[InteriorResult, BoundaryResult]

  Option 4B: Implement all mode, returns custom AllStickinessResults dataclass

  Option 4C: No all mode - users call wrapper multiple times or use run_qc() for multi-parameter analysis

  My lean: 4A (tuple return) because:
  - It's simple and explicit
  - No new types needed
  - Matches what run_qc() internally produces

  Interior Mode: Why Both Bounds Are Needed

  The Normalization Formula

  def compute_z(x, x0, L, U):
      max_dist = max(x0 - L, U - x0)  # Furthest distance from x0 to any bound
      z = np.abs(x - x0) / max_dist   # Normalized: z=0 at x0, z=1 at furthest bound

  What Each Bound Provides
  ┌───────┬─────────────────────────────────────────────────────────────┐
  │ Bound │                    Purpose in compute_z                     │
  ├───────┼─────────────────────────────────────────────────────────────┤
  │ L     │ Provides x0 - L (distance from x0 to lower bound)           │
  ├───────┼─────────────────────────────────────────────────────────────┤
  │ U     │ Provides U - x0 (distance from x0 to upper bound)           │
  ├───────┼─────────────────────────────────────────────────────────────┤
  │ max() │ Ensures z ∈ [0, 1] regardless of where x0 sits in the range │
  └───────┴─────────────────────────────────────────────────────────────┘
  Case Analysis: Missing Bounds

  Case 1: U=None (unbounded above)
  max_dist = max(x0 - L, None - x0)  # TypeError
  Even if we handle the None, what's the "max distance"? There's no upper limit, so samples far above x0 have undefined normalized distance.

  Case 2: L=None (unbounded below)
  max_dist = max(None - L, U - x0)  # TypeError
  Same issue in reverse.

  Case 3: Both None
  No scale reference at all. "Distance from x0" is meaningful, but "normalized distance" requires a scale.

  Why Normalization Matters

  The interior detection algorithm uses thresholds like eps = 10^-6. These thresholds assume z is normalized to [0, 1]. Without normalization:
  - A threshold of eps = 10^-6 might be huge (if the parameter range is 10^-9 to 10^-8)
  - Or tiny (if the parameter range is 0 to 10^6)

  The bounds provide the natural scale for the parameter.

  Possible Workarounds (Not Recommended)
  Approach: Use x0 - L only when U=None
  Problem: z can exceed 1, thresholds become meaningless
  ────────────────────────────────────────
  Approach: Use data-driven scale like std(x)
  Problem: Changes semantics; spike at x0 might be masked by spread
  ────────────────────────────────────────
  Approach: Use user-provided scale
  Problem: Adds parameter complexity, user burden
  My Recommendation

  Require both L and U for interior mode. This is not a limitation—it's mathematically necessary for the algorithm to work correctly.

  if mode == "interior" and (L is None or U is None):
      raise ValueError(
          "mode='interior' requires both L and U. "
          "Interior stickiness detection normalizes distance from x0 using the parameter bounds. "
          "For unbounded parameters, consider using mode='lower' or mode='upper' only."

  - Stickiness at x0 implies the optimizer failed to explore—but without bounds, there's no defined region to explore
  - The concept of "stuck at initial guess" is most meaningful when there ARE bounds the optimizer should be exploring within

  Revised: Interior Mode with Unbounded Parameters

  The Core Need

  You have:
  - Fitted values x from a legacy optimizer
  - Initial guess x0 that the optimizer may have stuck to
  - No bounds (or only one bound)

  You want to detect: "Did the optimizer fail to move from x0?"

  The Normalization Problem

  Without bounds, we need some scale to define "close to x0". Options:
  Approach: User-provided scale
  Formula: z = |x - x0| / scale
  Pros: Explicit, user controls meaning
  Cons: Extra parameter
  ────────────────────────────────────────
  Approach: Data-driven (std)
  Formula: z = |x - x0| / std(x)
  Pros: Automatic
  Cons: Spike at x0 deflates std, biasing result
  ────────────────────────────────────────
  Approach: Data-driven (IQR)
  Formula: z = |x - x0| / IQR(x)
  Pros: Robust to spike
  Cons: Still influenced by data shape
  ────────────────────────────────────────
  Approach: Data-driven (range)
  Formula: z = |x - x0| / (max(x) - min(x))
  Pros: Simple
  Cons: Outliers dominate; spike shrinks range
  FOR User-Provided Scale

  F1. Explicit Control
  The user knows their parameter's natural scale. For a rate parameter, maybe scale=1.0. For a log-parameter, maybe scale=0.1.

  F2. Consistent with Bounded Case
  When bounds exist: scale = max(x0 - L, U - x0) (derived from bounds)
  When bounds don't exist: user provides equivalent scale

  F3. No Data Contamination
  Data-driven scales are influenced by the very spike we're trying to detect. User-provided scale is independent.

  AGAINST User-Provided Scale

  A1. User Burden
  User must know what scale to use. For unfamiliar parameters, this may not be obvious.

  A2. Extra Parameter
  API becomes:
  detect_stickiness(x, x0, L=None, U=None, mode="interior", scale=???)

  FOR Data-Driven Scale (IQR)

  F1. Automatic
  No user input needed. Works out of the box.

  F2. Robust
  IQR (interquartile range) ignores outliers and isn't dominated by the spike.

  AGAINST Data-Driven Scale

  A1. Circular Reasoning
  If 30% of samples are stuck at x0, the IQR is computed on contaminated data. The "scale" is partially defined by the problem we're detecting.

  A2. Inconsistent Semantics
  With bounds: z=1 means "at furthest bound" (fixed reference)
  With IQR: z=1 means "one IQR from x0" (data-dependent reference)

  Thresholds tuned for bounded case may not transfer.

  def test_scale_std_produces_correct_normalization(self):
      """Verify std scale produces z-values consistent with std normalization."""
      rng = np.random.default_rng(42)
      # Create data with known std
      x = rng.normal(loc=10.0, scale=2.0, size=10000)
      x0 = 10.0

      # With scale="std", effective_scale ≈ 2.0
      # So z = |x - x0| / 2.0
      # For normal(0, 2), |x - x0| has mean ≈ 2 * sqrt(2/pi) ≈ 1.6
      # So mean(z) ≈ 0.8

      result = detect_stickiness(x, ref=x0, L=None, U=None, mode="interior", scale="std")

      # The mass curve at eps=1.0 should capture ~68% of samples (1 std)
      # Find index closest to eps=1.0
      idx = np.argmin(np.abs(result.eps_grid - 1.0))
      mass_at_1std = result.mass_curve[idx]

      # For |Z| where Z ~ N(0,1), P(|Z| < 1) ≈ 0.68
      assert 0.60 < mass_at_1std < 0.76, f"Expected ~68% mass at 1 std, got {mass_at_1std}"

      """Compute the normalization scale for distance calculations."""
      if L is not None and U is not None:

      if scale is None:
          raise ValueError(
              "scale parameter required when L or U is None. "
              "Use scale='std', 'iqr', 'range', or a float value."
          )

      if isinstance(scale, (int, float)):
          if scale <= 0:
              raise ValueError(f"scale must be positive, got {scale}")
          return float(scale)

      if scale == "std":
          s = np.std(x)
      elif scale == "iqr":
          q75, q25 = np.percentile(x, [75, 25])
          s = q75 - q25
      elif scale == "range":
          s = np.max(x) - np.min(x)
      else:
          raise ValueError(f"Unknown scale method: {scale}. Use 'std', 'iqr', 'range', or a float.")

      if s <= 0:
          raise ValueError(f"Computed scale is non-positive ({s}). Data may be constant.")

      return s
